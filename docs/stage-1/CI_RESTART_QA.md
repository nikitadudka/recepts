Основание — прямое поручение владельца диагностировать main после PR №12 и внести только подтверждённое минимальное исправление. База — актуальный `main` `b135dfb13b25da4432567ae907a0fe0988cb0741`, отдельная ветка `fix/ci-server-stdio`, worktree. A04 / PR №13 не изменяется.

## Доказательства и причина

Изучены AGENTS, PRODUCT, ARCHITECTURE, ROADMAP, DECISIONS, AGENT_WORKFLOW, README, QA_PLAN, QA_AUDIT, A10_1_QA, A22_QA, workflow и тестовый harness. Получены **полные** логи обеих job [main run 39807812539](https://github.com/nikitadudka/recepts/actions/runs/39807812539), а не только последние ошибки.

1. [Baseline 1](https://github.com/nikitadudka/recepts/actions/runs/39807812539/job/119925630257): syntax checks, 2 Node, 1 Pillow, 8 групп JSON API и smoke 01–13 проходят. В 15:47:36 UTC первый traceback полного набора — `subprocess.TimeoutExpired` на `tests/smoke.py:289`: `cls.server.wait(timeout=10)` в `test_14_server_restart_keeps_recipes_and_login`. Это ожидание **остановки старого** процесса, не готовности нового. До `Popen` нового сервера выполнение не дошло.
2. SIGTERM вызывает в приложении `server.close()`: listener закрывается, процесс ждёт завершения HTTP-соединений. Оставшиеся 31 smoke-тест получают `ECONNREFUSED` в setUp при входе на прежний порт. Это следствие прерванного перезапуска.
3. `BlockingIOError` возникает позднее в `unittest.result.printErrorList → stream.writeln → write` при печати накопленных traceback. Это ошибка вывода каскада, а не первый сбой сервера. Причина перехода конкретного runner FD в неблокирующий режим логом не установлена; отдельное изменение stdout/stderr без доказательства не вносилось.
4. До тестов в Baseline 1 есть `Task was destroyed but it is pending` / `TargetClosedError` при выходе из шага выбора пути Chromium. Шаг завершился success; затем фактический Chromium успешно запущен и проходят API и smoke 01–13. Это отдельная диагностическая аномалия, причинная связь с тайм-аутом остановки не доказана.

Подтверждённый дефект **тестовой инфраструктуры**: три сценария перезапуска обходили существующий `stop_server()` и предполагали, что graceful shutdown при живом браузере всегда завершится за 10 секунд. В cleanup уже был предусмотрен ограниченный TERM → ожидание → KILL → wait. Поведение A22 и JSON API не является причиной этого traceback. Свидетельств повреждения книги или ошибки обработки JSON нет.

Контролируемое воспроизведение на Node 24.19.0: открыть TCP-соединение, передать незавершённые HTTP-заголовки и оставить сокет открытым, проверить `/healthz`, отправить SIGTERM. Процесс остаётся жив дольше 10 секунд, новое подключение получает `ConnectionRefusedError`; закрытие удерживаемого сокета позволяет процессу завершиться с кодом 0. Новая браузерная регрессия вызывает исходный test_14 с таким соединением: на базе падает с тем же `TimeoutExpired`, после исправления проходит и проверяет рецепт/сессию. **Точный тип оставшегося соединения исторической CI job не записан**; не утверждается, что в ней был именно такой неполный запрос. Подтверждены ошибочное предположение harness и воспроизводимый механизм с той же цепочкой отказа.

## Проверка инфраструктуры и минимальное исправление

- `tests/smoke.py`: все три перезапуска (14, 40, 43) используют прежний `stop_server()`. При превышении прежних 10 секунд выводится явное сообщение о KILL. Новый процесс запускается после подтверждённого завершения старого; ошибка `kill/wait` продолжает падать. Проверки рецептов, входа и миграций сохранены.
- `tests/server_lifecycle_test.py`: детерминированное удержание незавершённого HTTP-соединения во время исходного браузерного test_14; проверены KILL старого процесса, запуск другого процесса, сохранение рецепта и сессии, финальная очистка процесса и временного DATA_DIR. Выбирается ровно один новый тест, унаследованные 45 не дублируются.
- `tests/ci_failure_checks.py`: запускает эту регрессию перед прежними отрицательными опытами. Уже существующий шаг Baseline 1 выполняет её с bundled Chromium. Ошибка регрессии даёт ненулевой exit. Workflow, условия matrix, зависимости, команды полного `npm test`, число существующих тестов и тайм-ауты не изменены; retries/задержек нет.
- `docs/ARCHITECTURE.md` и этот отчёт: описание жизненного цикла и воспроизведения.

Запуск: прямой `node server.js`, новый временный DATA_DIR, HOST loopback, унаследованные FAMILY_PASSWORD/PUBLIC_URL удаляются, `.env` не читается. Startup проверяет HTTP, затем `/api/setup` и API; рестарты проверяют `/healthz`, затем прежние данные через авторизованный запрос/браузер. Эти проверки проходят в регрессии. Начальная схема выбора порта — bind(0) с освобождением перед Node; теоретическое окно занятия порта есть, но в упавшем run сервер уже обслужил 13 тестов, ошибки bind/EADDRINUSE нет, новый сервер ещё не запускался. Изменять порты по этому инциденту оснований нет.

В smoke stdout сервера направлен в DEVNULL, stderr наследуется; непрочитанного PIPE для сервера нет. В A22 API stderr идёт в PIPE и читается при раннем exit, а при stop закрывается; в исследованном run все восемь групп прошли, насыщения PIPE не наблюдалось. Capture в `ci_failure_checks.py` использует `communicate`, process group и контроль временных каталогов. Cleanup smoke зарегистрирован сразу после создания ресурсов; актуальный процесс после restart доступен class cleanup, browser/context закрываются. Рабочая SQLite и пользовательские данные не использовались.

## Риски и передача

KILL применяется только к изолированному тестовому процессу после ожидания graceful shutdown; сохранность уже подтверждённой записи и сессии проверяется после открытия той же SQLite/WAL. Это проверка управляемого прерывания тестового сервера, не гарантия штатного graceful shutdown приложения при любых соединениях. Долгий graceful shutdown при незавершённом HTTP-запросе остаётся поведением приложения; изменять production shutdown для исправления harness не требуется. Новая регрессия добавляет примерно 15 секунд к Baseline 1, в том числе существующие 10 секунд grace.

Без нагрузочной сертификации, macOS/launchctl, реальных iOS/Safari/Android и независимого QA. Warning выбора Chromium и устойчивость вывода больших каскадов ошибок отдельно не исправляются. Для окончательной передачи нужны зелёные обе job Tests на head PR и проверка свежего main/конфликтов с открытым PR №13. Откат — revert только тестового исправления; данные восстанавливать не нужно. Следующий ответственный — владелец для review; merge, auto-merge и деплой не выполняются.
