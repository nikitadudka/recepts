## Безопасное и воспроизводимое окружение

После разрешения реализации QA использует отдельный checkout/worktree конкретного PR, Linux и закреплённые в A10 версии инструментов. Минимум Node.js ≥22.13; Python 3, Pillow, Python Playwright и Chromium. Версии из прошлого аудита — ориентир для предложения A10: Node 24.19.0, Python 3.12.14, Pillow 12.3.0, Playwright 1.62.0, Chromium 154.0.8037.57. Закрепление и установка тестовых инструментов в CI должны быть отдельно включены в одобренный объём; сейчас установки не выполняются.

Каждый API/браузерный набор получает **новый временный `DATA_DIR`**, свободный порт и `HOST=127.0.0.1`; прямой `node server.js`, без загрузки `.env`. Наследуемые `DATA_DIR`, `FAMILY_PASSWORD` и `PUBLIC_URL` не должны направлять проверку на рабочую установку. Тестовый пароль вымышленный; cookie и payload не публикуются. Существующий `tests/smoke.py` создаёт `TemporaryDirectory` и отдельный порт, но будущий harness должен также явно ограничить HOST loopback. Подготовку каталога `scripts/build-*` не запускать: она перезаписывает ресурсы.

Набор данных: встроенные восемь примеров + синтетические собственный рецепт, проба и копия каталога. Включить длинное название/ингредиент, многострочный шаг, неизвестные БЖУ `null`, `steps`/`instructions`, отсутствующий `shelf`, старые способы, фото data URL и `sample:`/`art:`, источник и избранное. Для поиска — отдельные фиксированные наборы 100 и 1 000 записей; не превращать это в нагрузочную сертификацию.

Для проверки сохранности получать `GET /api/library` до/после, сравнивать revision и семантическое содержимое всех рецептов; для фото — байты/хеш data URL и неизменность `art:`/`sample:`. Контроль `settings`/`sessions`, когда он нужен, вести только на изолированной тестовой SQLite read-only запросом, не выводя хеши/токены. Перезапускать сервер на **том же временном каталоге**, затем проверять сохранённое. При завершении остановить процесс, закрыть браузеры и очистить только созданный тестовый каталог.

Матрица интерфейса: обе темы (`classic`, `halloween`), viewport 320×740, 390×844, 768×1024 и 1440×1000; landscape 844×390. Это эмуляция Chromium. Отдельно реальные iOS/Safari и Android/Chrome: модель, OS, браузер и ориентация записываются в отчёт, проверяются экранная клавиатура, safe areas, фон/возврат и касания. Доступность: клавиатура, минимум один desktop screen reader и VoiceOver/iOS либо TalkBack/Android; недоступный инструмент/телефон имеет статус «Не проверен», не «Прошёл».

## A04 — устаревшие карточки после синхронизации

Общее условие: два независимых авторизованных browser contexts A и B, одна временная книга. В A выбрать фильтр/сортировку, прокрутить к рецепту и открыть его. В B менять запись через UI либо корректный API с **свежей** revision и полным снимком книги. Для ожидания polling использовать сетевой ответ A с нужной revision/изменённым содержимым и DOM assertion с ограниченным timeout; слепая задержка «спать 5 секунд» ненадёжна.

| Кейс | Шаги | Ожидается после исправления |
| --- | --- | --- |
| Q04-1: точная регрессия QA-01 | A открывает суп; B меняет название; дождаться принятия новой revision в A при открытом просмотре; закрыть Escape; повторить для крестика и backdrop | Сразу после закрытия карточка/список и число результатов отражают принятую revision; следующий `unchanged` не оставляет старый DOM. Повторное открытие показывает те же данные |
| Q04-2: несколько обновлений и удаление | Пока просмотр открыт, B меняет запись дважды либо удаляет её; дождаться последнего снимка; закрыть | Применяется последний снимок; удалённой карточки нет; нет воскрешения записи. В открытом просмотре согласованное уведомление объясняет удаление/обновление; кнопки не выполняют действие над устаревшим объектом |
| Q04-3: несохранённый редактор | A редактирует название, ингредиент, шаг и фото, не сохраняя; B меняет тот же рецепт; дождаться sync; отменить закрытие, затем сохранить | Ввод и позиция редактора не сбрасываются. Конфликт видим; исходная новая серверная версия не затирается. «Сохранить копию» сохраняет обе версии и поля; отмена закрытия оставляет форму открытой |
| Q04-4: другая запись / новый рецепт | A заполняет новый рецепт или редактирует X; B меняет Y; после sync сохранить A, затем закрыть | Незавершённый ввод остаётся; успешная запись использует актуальную книгу, не возвращает старый Y; после закрытия все карточки актуальны |
| Q04-5: каталог, пробы и вложенный переход | Открыть каталог/окно подключения/тему; в B добавить, перенести или удалить пробу; дождаться sync; закрыть. Повторить переход просмотр → редактор при уже отложенном обновлении | После закрытия последнего modal видны верные счётчики и main/trial/favorite; промежуточное закрытие не стирает редактор. Устаревший DELETE пробы, уже перенесённой B, даёт 409 и не удаляет основную запись |
| Q04-6: фокус, позиция, очередь | Закрыть обновлённый просмотр; повторить удаление исходной карточки, активный поиск, grid/list, затем быстрое избранное и polling | Фокус возвращается на сохранившийся инициатор либо заранее согласованный ближайший доступный элемент; не теряется в `body`. Поиск/сортировка и место списка сохраняются, если элемент остаётся. Очередь записи и защита 409 работают |

Автоматизация в fix PR: минимум Q04-1 и Q04-3, плюс удаление/последний снимок; остальные варианты — параметризовать либо документировать ручной результат. Для реального совместного чтения отдельно проверить уведомление и возврат на телефоне. Смена revision или перерисовка не должны сами записывать книгу.

## A22 — некорректный JSON

Точный предлагаемый контракт и порядок guards — [TECHNICAL_SPEC](TECHNICAL_SPEC.md). После одобрения контейнер тела — непустое тело с top-level JSON object, без массивов и `null`; `{}` допустим для операций без полей. **Единственное исключение — logout:** нулевое тело также допустимо ради совместимости; пробелы не считаются нулевым телом. Для login политика неверного/отсутствующего `password` остаётся 401, структура/синтаксис — 400. Проверка непустого тела logout и top-level trial-маршрутов — **предлагаемое расширение контракта**, а не уже существующая проверка.

| Маршрут | Предусловие, исключающее маскирующий guard | Проверка неизменности при отказе |
| --- | --- | --- |
| `POST /api/setup` | Новый отдельный DATA_DIR без пароля, локальный Host и loopback; не вызывать после успешного setup | Пароль и сессия не созданы; `needsSetup` остаётся true; книга/revision неизменны |
| `POST /api/login` | Тестовый пароль уже задан; счётчик попыток ниже 20 | Нет новой сессии/Set-Cookie успеха; книга/revision прежние. Счётчик попыток может увеличиваться по сохранённой политике limiter |
| `PUT /api/library` | Действующая сессия; правильные Origin и Content-Type | Все записи, фото, источники и revision совпадают с baseline |
| `POST /api/catalog/:id/save` | Действующая сессия и существующий catalog ID, выбранный фиксированным fixture | Нет новой записи/переноса/дубля и повышения revision |
| `POST /api/trials/:id/promote` | Действующая сессия, существующая синтетическая проба | Проба не перенесена, поля/revision сохранны |
| `DELETE /api/trials/:id` | Действующая сессия, существующая синтетическая проба | Проба не удалена, поля/revision сохранны |
| `POST /api/logout` | Действующая сессия; контроль входа через `/api/session` | Сессия не отозвана на некорректном теле; следующий защищённый GET доступен |

Для **каждого** маршрута выполнить матрицу Q22-1–Q22-6; setup и login получают собственные свежие fixtures. Login cases разбить на группы с новым сервером либо корректным успешным входом между группами, чтобы случайно не получить 429 вместо проверяемой ошибки. Setup после каждого корректного успешного запроса требует нового окружения.

| Кейс | Вход и шаги | Ожидается |
| --- | --- | --- |
| Q22-1: top-level | Literal `null`, `[]`, `[{}]`, строка `"text"`, числа `0`/`1`, `true`/`false`; `Content-Type: application/json` | 400, контролируемый JSON `{error: ...}`, без совета о диске/500; перечисленные выше инварианты соблюдены |
| Q22-2: синтаксис | Пустое тело, только пробелы, `{`, trailing comma, два JSON-объекта подряд | 400; ответ конечен, процесс жив; никакой частичной записи. Исключение: logout с нулевым телом — 200 и штатный отзыв текущей сессии; для него взять отдельный fixture и проверить последующий 401 |
| Q22-3: Content-Type | Отсутствующий заголовок, `text/plain`, `application/jsonp`, явно чужой charset; затем `application/json; charset=utf-8` и media type в другом регистре с валидным телом | 415 для неподдерживаемого media type/кодировки; разрешённый вариант доходит до обычной обработки. Не проверять заголовок через API-клиент, который автоматически подставляет JSON type |
| Q22-4: байтовые границы | Валидный объект с пробельным padding: `limit−1`, `limit`, `limit+1` байт; повторить с многобайтным UTF-8 текстом и chunked/без Content-Length | В пределах лимита нет 413 (дальше возможна ошибка полей); превышение — 413 по фактически прочитанным байтам, без записи. Лимиты: library 64 МиБ, остальные 4096 байт. При необходимости library проверять в ограниченном отдельном процессе |
| Q22-5: поля и revision | `{}`/неверный тип поля; library с валидными полями и устаревшей revision; затем корректный запрос со свежей revision | Ошибка полей 400 (login 401 по контракту); валидный stale library — 409; корректный запрос после отказов проходит и меняет только ожидаемые данные |
| Q22-6: порядок guards | Запрос с плохим Origin и типом/телом; без сессии; setup уже настроен; login после лимита; неизвестный catalog ID | Статусы соответствуют описанному приоритету 403/415/401/409/429/404. Ошибка тела не обходит защиту и не раскрывает приватные данные |

Дополнительно Q22-7: после серии отказов проверить `/healthz`, корректные login/setup/save/promote/delete/logout в новых fixtures; сравнить книгу и revision и повторить чтение после перезапуска. Сохранить прежнюю семантику идемпотентного catalog save и trial promote. Для oversize клиент может закрыть соединение; транспортное поведение должно быть зафиксировано и доведено до выбранного контрактом результата, а не объявлено успешным без ответа.

В регрессионном тесте отправлять **сырые байты** (особенно literal `null` и пустое тело): сериализация `None` библиотекой может означать отсутствие параметра. До любых успешных mutation-контролей сначала снять и сравнить baseline; иначе собственный контроль изменит revision и скроет ошибку. Каждый разрешённый граничный запрос, который способен выполнить mutation (например, logout с `{}` и padding), получает отдельный fixture: его штатный успех нельзя сравнивать как отказ без изменений.

## A10 — воспроизводимые тесты и CI

Предлагаемая разбивка исключает круговую зависимость: сначала A10 baseline/CI запускает существующий набор; каждый fix PR приносит свою регрессию и прогон; затем проверяется итоговый набор. CI не ждёт исправлений A04/A22 для появления workflow, а исправления не объявляются готовыми без профильного теста.

## Общая регрессия и передача владельцу

Для каждого PR поведения: `npm run check`, профильная новая регрессия и полный `npm test` перед готовностью; команды и exit code в PR. Прогон после существенного исправления повторяется на новом commit; зелёный результат старого commit не переносится автоматически.

Обязательная сохранность: создать/изменить/перезапустить; обе полки и избранное; фото/источники/ID; старые JSON и optional fields; экспорт→добавляющий импорт, изменённый совпавший ID копией; две сессии/409/сохранение копией; идемпотентный save и защищённое удаление пробы. Сравнивать семантические поля, не случайный порядок JSON-ключей. JSON round-trip не называется полным восстановлением SQLite. Для этого этапа не запускать миграции/backup реальной базы и не тестировать её на установленном Mac.

Шаблон отчёта в Issue/PR:

```text
Issue / PR / проверяемый commit / версия одобрения:
QA: отдельный агент или самопроверка Developer (указать явно):
Окружение и данные: OS, версии, viewport, тема, синтетический fixture:
Кейс → Прошёл / Не прошёл / Не проверен → доказательство/причина:
Реально выполненные команды и exit codes:
Сверка данных/revision/фото и результаты конфликтов:
Дефекты: шаги, expected/actual, влияние, безопасное доказательство:
Ограничения: реальные устройства, screen reader, недоступные проверки:
Рекомендация QA и следующий ответственный:
```

Нарушение сохранности/409, неработающий основной сценарий, воспроизводимая регрессия или несоответствие одобренному контракту блокируют рекомендацию «готово». Непроверенные реальные телефоны и screen reader явно остаются блокерами соответствующей мобильной/доступной приёмки; они не мешают рассмотрению документационного PR. QA возвращает дефект Developer в рамках одобренной задачи; изменение объёма — PM и владельцу. После проверки PM передаёт отдельный PR владельцу; QA не выполняет merge, auto-merge или деплой.
