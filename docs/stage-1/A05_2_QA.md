## Обнаруженные проблемы

- Classic: бледные подписи, подсказки, placeholder, метки БЖУ, строки ингредиентов/приготовления, счётчики и статус сохранения часто имели 2–3:1. Цвет ошибки редактора давал 4,08:1. Значимые края полей сливались с фоном; светлое кольцо клавиатурного фокуса давало 2,12:1.
- Halloween: большинство существующих текстовых пар уже проходило ориентир. Подпись бокового блока давала минимум 4,19:1 на его градиенте. Ошибка наследовала Classic и давала 3,72:1. Нативный placeholder пароля `#757575` на `#221b28` давал 3,63:1. Некоторые края контролов оставались около 1,6–2:1, в том числе отдельное mobile-правило кнопки темы.
- Первый CI на закреплённом Chromium 151 выявил ещё одну пару, которую локальный Chromium 154 оценил иначе: мобильная декоративная подпись «вечер для домашних чар» — **4,00:1** вместо локальных 4,83:1. Подпись осветлена с `#f1caa2` до согласованного `--ink` (`#f5ebdb`), без изменения размеров/позиции или ослабления теста; обе повторные CI-job подтвердили порог ≥4,5:1. Причина различия точных пикселей/растрирования шрифта между средами отдельно не локализована.
- Проверка только `backgroundColor` пропускала мобильный Halloween hero: под текстом находится соседняя иллюстрация с полупрозрачным градиентом. Реальный минимум ссылки — **3,26:1**, второй строки пояснения — **3,60:1**.
- `overflow:hidden` карточки обрезал наружный outline её внутренней кнопки. Полупрозрачные подложки значков/меток зависели от произвольного фото. Выбранный вид отличался бледной заливкой, мобильное подчёркивание Classic было недостаточно контрастным.

## Среда и ограничения

Linux; Node **24.19.0**, Python **3.12.14**, Playwright **1.62.0**, Pillow **12.3.0**; фактический локальный **Chromium 154.0.8037.57** (`/usr/bin/chromium`). Только синтетические fixtures/вымышленные записи, отдельные браузерные контексты, loopback-порт и временный `DATA_DIR` из существующего harness. Настоящие SQLite/экспорты/фотографии пользователей не открывались. Диагностические логи, JSON замеров и screenshots находятся в `/tmp` и не включены в PR.

- Реальные iOS/Safari, Android/Chrome, macOS, VoiceOver/TalkBack/NVDA недоступны и **не проверены**. Native file chooser, камера, клавиатура телефона, safe areas/rotation и нативное оформление контролов других браузеров требуют device QA.
- Это ограниченная проверка контраста и фокуса в Chromium, **не заявление полного соответствия WCAG AA**. Обычный текст проверяется ≥4,5:1, крупный ≥3:1; целевые значимые края/иконки/маркеры и focus ≥3:1. Комплексный accessibility-аудит, все страницы/платформы, печать, forced-colors и весь каталог из 1567 вариантов не исследованы заново.
- Консервативные stop-замеры не моделируют произвольные sibling overlays; для фактического hero это закрывает отдельная пиксельная проверка. Полупрозрачная подпись иллюстрации каталога имеет тёмную подложку; смена её изображения/градиентов требует повторной проверки. Фото-кнопки защищены непрозрачными поверхностями и двумя цветами focus, но это не аудит любых будущих пользовательских CSS/изображений.
- Скрипт проверяет нативные checkbox/focus и выбранные состояния в текущем Chromium. Пиксельное устройство каждой нативной галочки/меню браузера и каждой фазы анимации отдельно не сертифицируется. Неактивные контролы сохраняют прежнюю opacity и являются исключением, а не доказанным 4,5:1.
- Реальный browser/text zoom и screen reader не заменяются изменением viewport. Существующие узкие smoke-сценарии сохраняются; новые измерения контраста ограничены указанными двумя ширинами. Состояния и ошибки A06 не перепроектируются.

Рекомендация самопроверки: передать владельцу на review с перечисленными ограничениями. Без подтверждения владельца не закрывать Issue №7.

## Безопасный откат

1. Пока PR не объединён — оставить его незамерженным. `main`, размещённое приложение и данные не изменены.

### Tab: причина и границы вывода

DOM-порядок при закрытых фильтрах: поиск → кнопка «Фильтры» → пять быстрых условий → select сортировки → «Плитка» → «Список» → карточки. При раскрытии фильтров между «Фильтры» и быстрыми условиями появляются семь select и «Сбросить». Скрытые auth/file/dialog-поля в Tab не участвуют. Положительных tabindex нет; `-1` у заголовков используется только для программного возврата A04. Размещение элементов не менялось.

Проверены все `.focus()`, focusin/keydown, render, refreshLibrary/polling, диалоги и минутное применение темы. Обработчик `/` не перехватывает Tab/Shift+Tab. Render заменяет выдачу/заголовок, **сохраняет узлы поиска/сортировки/панели**; focus A04 восстанавливается для карточек, а при фокусе в select/поиске сохранён. При реальных Tab/Shift+Tab и remote revision инструментирование `HTMLElement.prototype.focus` не зарегистрировало программных перехватов. Последовательность в Chromium предсказуема в обе стороны; после сортировки Tab идёт к виду, не в поиск.

Сообщённая последовательность совместима с **ограниченным режимом клавиатурной навигации Safari/macOS**, когда Tab пропускает кнопки и ссылки, оставляя текстовые поля/некоторые select и переходы через browser chrome. Тогда из панели книги остаются поиск и сортировка; возврат к поиску сам по себе не доказывает trap сайта. Фактическая настройка на Mac владельца пока не подтверждена; поэтому это диагностическое объяснение, а не объявление исправления/успешного Safari QA. Для отделения настройки от дефекта обязательна проверка ниже. Код приложения для принудительного обхода настройки не добавлен, tabindex/Tab-handler/компоновка не изменялись.

### Кошка: установленная причина и исправление

Дефект воспроизведён в Chromium на фазе **2,4 s**: справа **за** bbox SVG находятся отделённые вертикальные светлые фрагменты. На тёмном фоне они заметнее. Исходная PNG RGBA 1536×1024 не содержит широкой непрозрачной белой границы: на крайнем правом краю максимум альфы 1/255, bbox альфы >8 — `(15,6,1511,763)`. Цветной RGB под нулевой альфой не является сам по себе видимой полосой. PNG не очищалась/не заменялась.

Установленная причина — рассогласованные области: фильтр имел `x=-100,y=-50,width=1736,height=1124`, а его карта `feImage`/внешний SVG покрывали только `0,0,1536,1024`. Вне карты получается прозрачный чёрный (`R=G=0`), а не нейтральное `R≈G≈0,5`. По формуле displacement `scale*(channel-0,5)` это ненулевое смещение; при анимации оно повторно выбирало светлый край SourceGraphic и давало отделённые фрагменты. Это воспроизводимый дефект ресурсов/фильтра, не предположение о CSS transform или обязательная особенность Safari.

В `index.html` области обеих feImage и в `assets/cat-tail-motion.svg` / `assets/cat-paw-motion.svg` viewBox/нейтральная подложка расширены до полной области фильтра. Координаты эллипсов и gradient stops, PNG, логотип, CSS, параметры scale/SMIL и reduced motion сохранены. Clipping/overflow и размеры интерфейса не менялись. В диагностике после исправления отделённых фрагментов нет на фазах 0 / 1,1 / 2,4 / 3,51 / 3,8 / 5,2 / 6,5 s; движение хвоста/лапки остаётся.

Прежний test_25 снимал bbox логотипа, поэтому не видел артефакт за его правой границей. Новый test_66 снимает с запасом справа: обе темы, 1440/390×1000, синтетический DPR 2, несколько фаз, сохранность движения и reduced motion. **Это не реальный Retina/Safari.** Negative control с исходными index/maps из `7f017fa`: ожидаемый exit 1, `classic 1440 phase 2.4: displaced right-edge fragments`; тот же test на исправлении проходит. Все прежние 75 тестов сохранены.

Текущая задача ограничена PNG: без изменений кода, CSS, SVG, анимации, других исходных изображений, API или данных. Самопроверка одним агентом, не независимый QA.
