## A10 — воспроизводимые тесты и CI

**Приоритет:** P1, очередь 1; **сложность:** M. Ведущий — Developer / Architect, контракт проверок согласует QA Engineer.

**Проблема и ценность.** По QA/TECH-аудиту текущие 46 тестов прошли в одном окружении, но Python-инструменты/браузер не закреплены, GitHub Actions отсутствует. Разные окружения затрудняют воспроизведение дефектов; автоматическая проверка каждого маленького PR сокращает вероятность регрессии сохранения.

**Предлагаемое решение.** A10.1 — один PR с воспроизводимой конфигурацией **существующих** test-инструментов и CI `npm run check` + `npm test`. Версии, ОС, Chromium, подготовка и обновление описаны в TECHNICAL_SPEC. Новые библиотеки/производственные зависимости не нужны. Установка отсутствующих инструментов в чистом будущем runner требует отдельного разрешения владельца в составе A10.1; в текущем PR ничего не устанавливается. Регрессии A04/A22/A05 и следующих UI-задач добавляются вместе с их исправлениями, затем A10 сверяет их запуск в CI.

**Компоненты.** Предлагаемые `.github/workflows/…`, файл фиксации Python test-инструментов, `docs/ARCHITECTURE.md`/QA-инструкции; `tests/install.test.js`, `tests/images_test.py`, `tests/smoke.py` и `package.json` — только если требуется согласованная команда. Точные новые пути сначала в PR, без реорганизации runtime.

**Риски и зависимости.** Доступность версий и системных библиотек Chromium, flaky ожидания, чувствительные artifacts, права Actions. Установки и точная конфигурация ждут одобрения; данные — синтетические. A10.1 не ждёт исправлений. Закрытие A10 ждёт фактических регрессий одобренного объёма. Не включать deployment, branch protection или секреты автоматически.

**Критерии приёмки.**

1. В чистой одобренной среде по документированной команде проходят `npm run check` и полный текущий `npm test`: исходный baseline 2 Node + 1 Pillow + 43 smoke = 46. Новые тесты увеличивают число, не заменяют старые проверками слабее.
2. CI работает на PR, с минимальными правами чтения репозитория, без доступа к рабочей книге, секретам и деплою; отсутствующий браузер или test-инструмент завершает job ошибкой, а не успешным skip.
3. Временные БД/процессы изолированы и очищаются; logs/artifacts не содержат cookie, паролей и личных данных. Логи версий доступны для воспроизведения.
4. По мере приёмки A04/A22/A05–A07 их содержательные регрессии выполняются в том же pipeline; failure даёт ненулевой exit без подавления/retry до зелёного.
5. Повтор на отдельном чистом runner воспроизводим; записаны результаты и ограничения Linux относительно реальных телефонов/macOS.

**QA.** QA-матрица A10 в QA_PLAN: чистый запуск без cache, сравнение количества/статусов тестов, негативная проверка отказа job при недоступном браузере/падающем тесте, изоляция DATA_DIR, отсутствие publish/секретов. Негативный прогон — на временной ветке/копии, без намеренно сломанного коммита в main. «Сейчас 46 tests pass» не заявляется без нового прогона.

**Граница PR.** A10.1 — baseline/CI; новые дефектные сценарии — в соответствующем fix PR. Владелец отдельно подтверждает настройку test-окружения. Далее QA → review владельца.

## A22 — некорректный JSON возвращает контролируемую ошибку

**Приоритет:** P1 этапа, очередь 2 (исходный QA-02 — P2); **сложность:** S/M. Ведущий — Developer / Architect; PM/QA согласуют контракт.

**Проблема и ценность.** QA-02 подтвердил HTTP 500 для literal `null` на login/library: после parsing поля читаются без проверки контейнера. Ошибка входных данных выглядит как авария диска/сервера. Пользователь и интеграция должны получать понятный отказ без изменения книги и без ложного сообщения о проблеме хранения. Потеря данных исходным опытом не доказана.

**Предлагаемое решение.** Проверить non-null object до чтения полей и до мутации на всех существующих изменяющих маршрутах. Сохранить `{error: string}` и действующие guards. Предлагаются 400 для неверного JSON/контейнера, 415 для неподдерживаемого media type, 413 для превышения прежнего лимита; 401/403/404/409/429 остаются по контракту TECHNICAL_SPEC. Пустой logout сохраняет совместимость как отдельное исключение; непустой logout обязан быть JSON object. Новый список API не нужен для этого исправления.

**Компоненты.** `server.js`: helper чтения body, Content-Type и обработчики setup/login/logout/catalog-save/trial-promote/trial-delete/library-put; `tests/smoke.py`, описание API/QA. Схема БД и поля рецептов не меняются.

**Риски и зависимости.** Порядок Origin/Content-Type/auth/setup/rate-limit guards, обратная совместимость login и body-less logout, лимиты в байтах и преждевременная транзакция. Требуется одобрение точной матрицы ошибок/исключения logout. A10.1 — рекомендуемая организационная зависимость, новый UI и A07 не нужны.

**Критерии приёмки.**

1. Для всех семи route/method-пар из TECHNICAL_SPEC проверены `null`, array, string, number, boolean, пустое тело, битый JSON, правильный object, неверный Content-Type и лимит. При нарушении структуры — документированный 4xx, никогда общий 500.
2. `application/json; charset=utf-8` допускается; ложный префикс вроде `application/jsonx` отвергается. Проверены ровно лимит и лимит+1 байт, включая многобайтный текст. Лимиты не увеличены.
3. Все отклонённые запросы оставляют содержимое книги, фото, источники, ID и revision неизменными. Некорректные setup/login/logout не создают/не отзывают сессию и не меняют пароль; счётчик попыток входа по прежней политике может увеличиться.
4. Следующий корректный запрос проходит; настоящие 401/403/409/429 и защита stale trial остаются. Health 200 не подменяет проверку данных.
5. Старые корректные клиенты/import/export совместимы; пустой logout и logout `{}` успешны, пустые остальные body — 400 при пройденных guards.

**QA.** Таблица A22 в QA_PLAN: отдельные свежие setup-окружения, авторизованная сессия, существующие catalog/trial IDs, сброс login-rate-test через новый процесс, snapshot книги/revision до/после каждого отказа, успешная операция после отказа. Защищённый запрос без сессии может получить 401 раньше parsing; приоритет нескольких ошибок проверяется по TECHNICAL_SPEC.

**Граница PR.** Один fix PR: серверная валидация + регрессии + актуальное описание ошибок. Без рефакторинга роутера/авторизации и изменения модели данных.

## A04 — актуальные карточки после синхронизации

**Приоритет:** P1, очередь 3; **сложность:** S/M. Ведущий — Developer / Architect; поведение открытого окна уточняет UX/UI.

**Проблема и ценность.** QA-01/UX-14: polling принимает новый snapshot/revision при открытом dialog, `render()` пропускается. Закрытие и последующий `unchanged` не обновляют карточки. Список и подробности расходятся; участник должен видеть одну актуальную книгу без перезагрузки.

**Предлагаемое решение.** Пометить отложенную перерисовку после remote change и применить, когда последний dialog действительно закрыт. Обрабатывать все способы закрытия и переходы между окнами. Сохранить запрос/фильтры/сортировку/вид и логическую точку фокуса. В открытом просмотре — доступное уведомление об изменении/удалении и явное обновление; dirty-редактор не заменять. Точное поведение в UX/TECHNICAL_SPEC требует одобрения, не включает редизайн карточек.

**Компоненты.** `app.js`: `refreshLibrary`, `render`, закрытие/cancel/backdrop/переходы dialog, защита editingSnapshot и writeQueue; локальная разметка/стиль уведомления при необходимости; `tests/smoke.py`.

**Риски и зависимости.** Потеря focus/scroll при замене DOM, перерисовка между двумя modal, затирание формы, устаревшее delete/promote, путаница «сервер обновился» и «моя правка сохранена». A04 не ждёт нового каталога или layout A06. Связанные изменения dialog в A05.1 интегрируются после A04 и повторяют его регрессию.

**Критерии приёмки.**

1. Сессия A открывает рецепт; B меняет его; A получает новую revision, закрывает окно и **сразу** видит актуальную карточку без reload и ожидания следующего polling. Повторный `unchanged` не возвращает старое.
2. Проверены Escape, крестик, backdrop, программное закрытие, открытые просмотр/каталог/редактор и несколько последовательных remote updates. Перерисовка не разрушает ещё открытый modal.
3. Если запись удалена/перенесена или перестала соответствовать фильтру, карточка исчезает/перемещается корректно; focus возвращается к той же записи либо к заголовку выдачи, если её нет. Состояние поиска и фильтров сохраняется.
4. В открытом просмотре новая версия не подменяется молча: видно изменение, явное обновление показывает актуальные поля. При удалении закрытие/возврат безопасны, устаревшее действие не восстанавливает запись.
5. Несохранённые название/ингредиенты/шаги/фото остаются в форме при remote change. Cancel закрытия оставляет форму; save конфликтующей записи по-прежнему предлагает копию. Сохранение в очередь и revision/409 не ослаблены.

**QA.** Сценарии A04 в QA_PLAN: два браузерных контекста, ожидание фактического GET с новой revision вместо фиксированного sleep; edit/delete/promote; активные фильтры, grid/list, обе темы; dirty-форма и отмена закрытия, конфликт и сохранение копии; проверка API/revision и DOM, не только toast.

**Граница PR.** Один fix PR с уведомлением и регрессией. Общий redesign диалогов не нужен; контраст/keyboard A05 остаются отдельными PR.

## A05 — контраст, клавиатура и доступные диалоги

**Приоритет:** P1, очередь 4; **сложность:** M, два PR. Ведущий — UX/UI Designer & Researcher до одобрения; затем Developer / Architect.

**Проблема и ценность.** UX-01: несколько текстов classic имеют 2,48–3,14:1; UX-02: фото нельзя выбрать Tab/Enter; UX-03: dialog рецепта не имеет доступного имени; UX-06: выбранные коллекции/фильтры сообщаются только цветом. Слабовидящий пользователь и пользователь клавиатуры должны завершать те же действия.

**Предлагаемое решение.** A05.1 — доступная нативная загрузка/кнопка фото, имя каждого dialog, выбранные состояния, видимый focus, возврат focus и ненавязчивые объявления результата/ошибки. A05.2 — согласованные контрастные токены обеих существующих тем, сохранение визуального характера. Конкретные цвета/состояния — в MOBILE_UX_SPEC, без новых UI-библиотек и без новой темы.

**Компоненты.** `index.html`, `app.js` (динамические заголовки, состояния и обработчики), `style.css`, `halloween.css`, `catalog.css`; `theme.js` только при необходимости сохранения одобренных функциональных названий; профильные браузерные тесты.

**Риски и зависимости.** Каскад тем, фокус после DOM-update A04, лишнее озвучивание результатов при вводе. Одобрение UX и palette обязательно; A05.1 следует после A04 для безопасной интеграции общих dialog-handlers, хотя семантически исправления независимы. Названия каталога и состояния выдачи при изменении темы координируются с A07, без дублирования владельцев DOM.

**Критерии приёмки.**

1. Обычный текст ≥4,5:1, крупный ≥3:1; значимые границы/иконки контролов и focus ≥3:1 к соседним цветам там, где требуется. Таблица замеров охватывает темы и default/hover/focus/selected/error, включая ранее найденные пары; текст на изображениях проверяется отдельно.
2. Keyboard-only путь «создать → ингредиенты/шаги → фото → сохранить → открыть → редактировать» завершён. Фото доступно Tab, Enter/Space; отмена file chooser не меняет рецепт, удаление фото озвучено.
3. Все dialog имеют доступное имя, логичный начальный focus, Tab/Shift+Tab внутри modal, Escape и возврат focus. Dirty-form confirmation и A04 сохраняются.
4. Selected states коллекций/быстрых условий/вида доступны семантически, ошибка связана с полем, число результатов объявляется без постоянного повторения всей сетки.
5. Обе темы, zoom 200% и reduced motion не блокируют действия. Screen-reader результаты записаны с названием/версией инструмента; полный WCAG AA не объявляется по нескольким проверкам.

**QA.** A05 в QA_PLAN: измерение контраста и keyboard без мыши, доступное дерево/имена/labels, VoiceOver/TalkBack/NVDA при доступности, фокус при remote update и закрытии из каждого пути. Отсутствие реального screen reader — явный пробел, не автоматический pass.

**Граница PR.** A05.1 — keyboard/semantics/dialog, A05.2 — цвета/focus styling. Каждый связан с одной Issue и собственным QA; код дизайна до одобрения не меняется.

## A06 — мобильные главная, редактор и чтение

**Приоритет:** P1, очередь 5; **сложность:** M на каждую часть. Ведущий — UX/UI Designer & Researcher до одобрения.

**Проблема и ценность.** UX-04: на classic 390×844 поиск начинается около y=754, в Halloween декор ещё выше; UX-05: маленькие элементы; UX-10: скрыт постоянный статус несохранённых изменений; UX-11: поле ингредиента 126 px на 320. Повторному пользователю нужны быстрый поиск, уверенность в сохранении и удобный ввод на смартфоне.

**Предлагаемое решение.** A06.1 — компактная шапка с кошкой, книга/каталог как явные входы, поиск до большого декора, удобные фильтры и действия; постоянный компактный status при saving/error. A06.2 — полноширинное название ингредиента, количество/единица/удаление ниже; читаемый рецепт и расположение действий; клавиатура и safe area. Макеты, размеры и все состояния — в MOBILE_UX_SPEC. Форматы полей и действующие категории не меняются.

**Компоненты.** `index.html`, `style.css`, `halloween.css`, `catalog.css`, точечные `app.js` status/focus handlers; профильные UI-проверки. Новые layout-файлы приложения не создаются без необходимости.

**Риски и зависимости.** Перекрытие keyboard/footer, избыточное уплотнение, потеря скролла/фокуса, скрытие error после успешного polling, desktop-regression. Нужны одобрение макетов и принятые A04/A05. A06.1 не ждёт нового API A07: старый каталог должен продолжать работать. A06.2 может следовать независимо от A07.

**Критерии приёмки.**

1. На 390×844 в обеих темах поиск, вход добавления и начало выдачи видны без прокрутки большого hero; конкретные зоны сравниваются с одобренным макетом. На 320 px нет горизонтальной прокрутки основных экранов, длинные названия не перекрывают действия.
2. Основные мобильные цели — ≥44×44 CSS px как продуктовый ориентир; WCAG 2.5.8 (24 px/исключения) оценивается отдельно. Контраст и focus A05 не регрессируют.

## A07 — поиск и обозримый каталог

**Приоритет:** P1, очередь 6; **сложность:** S/M API + M UI. Ведущие — UX/UI и Developer / Architect, критерии поиска утверждает PM.

**Проблема и ценность.** UX-07: при 1 567 совпадениях показана одна случайная идея; сравнить варианты нельзя. UX-06/12: активные условия плохо сообщаются невизуально, сезонная тема меняет функциональное имя. Пользователь должен осознанно выбрать рецепт, вернуться к выдаче и понимать, что уже сохранено.

**Предлагаемое решение.** A07.1 — минимальный авторизованный read-only endpoint ограниченной детерминированной выдачи: `q`, `kind`, сортировка title/time, постраничное «Показать ещё» по контракту TECHNICAL_SPEC. Текущий `/api/catalog` содержит только total/counts, списка нет; использование выдуманного готового API недопустимо. A07.2 — список совпадений с названием/временем/разделом, отдельная случайная идея, видимый итог условий и сброс, сохранение позиции/query при возврате из подробностей. Поиск книги сохраняет действующие правила всех слов, ё/е и простых окончаний. Новая морфология и диетические обещания не добавляются.

**Компоненты.** `catalog.js` (read-only поиск/сортировка/порции результата), `server.js` (новый GET, валидация параметров/auth), `app.js` (запрос/гонки/выдача/сохранение/возврат), `index.html`, `catalog.css`/темы, при необходимости `theme.js` для одинакового функционального названия; API/browser регрессии.

**Риски и зависимости.** Это расширение API, требует отдельного явного одобрения контракта. Риски: скачивание всего каталога, гонка ответов, нестабильный порядок, потеря условий, дубли/перезапись сохранённых правок, регресс random. A07.1 технически независим от mobile layout; рекомендован после подтверждённых исправлений. A07.2 зависит от A07.1, A05 и A06.1. Новые фильтры времени/инвентаря, пообъектный API книги A11 и изменение каталожного JSON не входят.

**Критерии приёмки.**

1. Поиск с ≥10 совпадениями показывает сравнимый список; размер страницы ограничен, дальнейшая выдача по явному действию, без фоновой загрузки всех 1 567 записей. Стабильная сортировка и отсутствие пропусков/дублей при переходах по страницам.
2. Корпус: регистр/ё–е/пробелы/простые окончания/все слова, название и ингредиенты, запрос без совпадений; ожидаемые ID зафиксированы до реализации. Каталог и книга не смешивают данные, область поиска ясно подписана.
3. `q/kind/sort`, активные условия и позиция сохраняются при просмотре/назад в рамках текущего открытия каталога; новый запрос сбрасывает страницу. Старый медленный ответ не заменяет новый. Нулевой результат, загрузка, error/retry и конец списка различимы.
4. Random доступен отдельным действием и учитывает его документированные условия. Смена темы сохраняет функциональные названия, запрос и выбранный раздел.
5. «В книгу»/«На пробу» подтверждаются сервером, повторное сохранение не даёт дубля и не затирает пользовательские правки/фото/источник. Устаревшее удаление пробы не удаляет уже перенесённое. Чтение каталога не меняет revision книги.

**QA.** A07 в QA_PLAN: контракт API и неверные query/limit/sort, два context save/promote/stale-delete, повторное сохранение изменённой копии, быстрая смена запроса при задержке ответов, keyboard/screen reader, обе темы и мобильные размеры. Каталог по-прежнему read-only относительно своих исходников, права/атрибуция и ID сохраняются.

**Граница PR.** A07.1 — endpoint+контрактные тесты, A07.2 — UI+browser-регрессии. Закрывать Issue только после обеих частей; API PR сам по себе не объявляет UX-задачу выполненной.
