## A04: применить отложенное обновление карточек

**Факт:** [`refreshLibrary()`](../../app.js#L37) принимает новый снимок и `revision`, но пропускает `render()` при любом открытом диалоге. После закрытия ни обработчик крестика, ни Escape/backdrop не применяют отложенное обновление; следующий polling получает `unchanged`. Это QA-01, рассогласование DOM и уже принятого состояния. Потеря серверных данных этим дефектом не доказана.

**Минимальное решение:** хранить отдельный признак необходимости перерисовки книги. При принятии снимка ставить его; при отсутствии открытых диалогов применять обновление сразу. На событии `close` каждого диалога проверять признак и применять актуальное состояние, только когда больше нет открытых диалогов. Событие `close` покрывает крестик, Escape, backdrop и программное закрытие; не размножать одинаковую логику во всех click-ветках. Несколько принятых снимков объединяются в одну перерисовку последней версии. Обычный `unchanged` не должен стирать признак.

При переходе «просмотр → редактор» старый диалог закрывается, новый открывается синхронно: обработчик не должен перерисовать книгу и украсть фокус из редактора. После обновления сохранить запрос, фильтры, сортировку, grid/list и прокрутку. Возврат фокуса искать по ID и действию заново: исходный DOM-узел карточки мог быть заменён. Если запись исчезла из текущей выдачи, фокус — на заголовок результатов, без скачка страницы. Не менять форму, `formDirty`, `draftImage`, `editingSnapshot` или курсор пользователя при polling.

**Предлагаемое поведение открытого просмотра для одобрения:** не заменять читаемый текст под пользователем автоматически. Для изменённого рецепта показать доступное уведомление «Рецепт изменён на другом устройстве» и действие «Обновить просмотр»; оно перечитывает уже принятую версию и сохраняет близкую позицию чтения, ограниченную новой высотой. Для удалённого — «Рецепт удалён на другом устройстве» и «Вернуться к книге»; недоступные действия над исчезнувшей записью выключены. Для перенесённой пробы обновляются состояние полки/доступность действий, нельзя отправить устаревшее удаление основной записи. В редакторе ввод сохраняется; прежняя проверка конфликта при сохранении остаётся. Это небольшой статус и поведение синхронизации, а не новый режим готовки или история версий.

Компоненты: `app.js` (`refreshLibrary`, `showRecipe`, `render`, обработчики закрытия и возврата фокуса), минимальная разметка/стиль уведомления при необходимости, `tests/smoke.py`. Сервер, API и SQLite не меняются. A05 затем проверяет доступность этого уведомления вместе с остальными диалогами.

Альтернативы: безусловный `render()` после каждого `close` проще, но пересоздаёт карточки без обновления и мешает фокусу; live-перерисовка всего открытого диалога сбрасывает чтение и опасна для формы. Рекомендуется отложенный флаг с явным обновлением просмотра. Риск — лишний рендер/потерянный фокус; ограничить точкой применения и проверить переход между диалогами.

Приёмка/QA: две сессии, remote edit/delete/promote при открытом просмотре, редакторе и каталоге; закрыть через Escape/крестик/backdrop/программный переход. После последнего закрытия карточки соответствуют последней принятой `revision` сразу, без ожидания ещё одного polling. Запрос/вид/фильтры/позиция сохранены; форма и фото не меняются; конфликт даёт прежнее сохранение копией. В тесте ждать ответ с новой `revision`, а не фиксированные пять секунд. Прогнать существующие проверки двух устройств, stale trial actions и импорта.

## A22: контролируемые ошибки JSON на всех мутациях

**Факт:** [`body()`](../../server.js#L50) ограничивает число реально прочитанных байтов и разбирает JSON; пустое тело уже даёт 400. `null` успешно разбирается, затем `input.password`/`input.revision` дают исключение и общий 500. У `catalog/save` такая же небезопасная разыменовка. Действия с пробами читают JSON, но игнорируют структуру; logout вообще не читает тело. Общий Content-Type guard сейчас принимает любой префикс `application/json`, включая неверный `application/jsonp`.

### Предлагаемый контракт v1 для одобрения

Сохранить envelope ошибок `{ "error": "понятный текст" }`, `application/json; charset=utf-8`, `Cache-Control: no-store`. Не добавлять обязательный новый `code` и не менять успешные DTO.

| Метод и маршрут | Тело и лимит | Поведение после проверки контейнера |
| --- | --- | --- |
| `POST /api/setup` | Ненулевой JSON object, 4 096 байт | `password` 8–128 символов; прежние запрет удалённого setup и повторная проверка уже заданного пароля сохраняются |
| `POST /api/login` | Ненулевой JSON object, 4 096 байт | Неверный/отсутствующий `password` остаётся 401; структурно неверное тело — 400; существующий лимит попыток сохраняется |
| `POST /api/logout` | **Исключение совместимости:** нулевое тело либо JSON object, 4 096 байт | Только после успешной проверки отозвать текущую сессию; пустое тело исторически работало. Сам клиент уже шлёт `{}` |
| `POST /api/catalog/:id/save` | Ненулевой JSON object, 4 096 байт | `{}` сохраняет прежний default `destination: main`; `main`/`trial`, дедупликация и транзакции прежние |
| `POST /api/trials/:id/promote` | Ненулевой JSON object, 4 096 байт | `{}` допустим; защита повторного переноса сохраняется |
| `DELETE /api/trials/:id` | Ненулевой JSON object, 4 096 байт | `{}` допустим; запись, уже ставшая основной, по-прежнему не удаляется |
| `PUT /api/library` | Ненулевой JSON object, 67 108 864 байта (64 МиБ) | Прежняя валидация `revision`/`recipes`, уникальных ID, лимита 10 000 и каждого рецепта; прежний CAS/409 и атомарная транзакция |

JSON object означает `value !== null`, `typeof value === 'object'`, `!Array.isArray(value)`. `null`, массив, строка, число, boolean, битый JSON и непустой поток из одних пробелов возвращают 400. Нулевое тело — 400, кроме указанного logout. Не запрещать неизвестные ключи автоматически: минимальная задача не вводит новую строгую схему всех объектов. Валидация полей рецептов остаётся прежней.

Content-Type: media type после удаления параметров и пробелов должен быть ровно `application/json` без учёта регистра; `application/json; charset=utf-8` допустим. Отсутствующий/чужой media type и `application/jsonp` — 415. Поддерживается UTF-8; явно объявленная другая кодировка — 415. Лимит считается по поступившим байтам, независимо от отсутствия/неправдивого `Content-Length`, до JSON parsing. Разрешённый размер включительно принимается к дальнейшей проверке; размер +1 байт — 413. Лимиты не повышаются. Реализация должна вернуть читаемый 413 клиенту и обработать оставшийся поток безопасно, без попытки повторно ответить после закрытия соединения.

Это предложение унифицирует отказ на `null`/необъектных телах у проб и вводит проверку непустого тела logout. Оно **не описывает уже существующее поведение** этих маршрутов. Совместимость body-less logout сохраняется намеренно; `app.js` уже посылает `{}` для logout/обоих trial actions. Публичного API-клиента не обнаружено, но это не доказывает отсутствие внешних клиентов; новый контракт должен быть явно указан в Issue/PR.

### Порядок ошибок

Не переносить body parsing перед защитными проверками ради одинакового ответа. Последовательность:

1. Общий Origin guard → 403; затем Content-Type guard → 415.
2. Для setup — прежние «уже задан пароль» 409 / недопустимый локальный доступ 403; для login — ограничитель попыток 429; для защищённых маршрутов — отсутствие сессии 401.
3. Для catalog save проверка существования ID остаётся до чтения body: неизвестный ID → 404. Для trials существование/полка проверяются после body, как сейчас.
4. Чтение в пределах лимита → 413; syntax/top-level → 400; затем поля → 400 (неверные учётные данные login → 401).
5. Согласованный валидный объект доходит до прежних проверок существования/полки/`revision`, 404/409 и транзакций.

Поэтому запрос с несколькими ошибками получает **первую** по этому порядку, а не всегда 400. Размер проверяется, только если поток читается: например, неавторизованный PUT с oversized body остаётся 401. Не обещать ответ JSON на физически оборванное клиентом соединение.

### Инварианты и проверки

На отклонённом запросе не меняются книга, `revision`, пароль и действительность сессии (в частности, невалидный logout не выходит из книги). Исключение — счётчик попыток login, который намеренно увеличивается защитным guard до чтения body. Ошибка не должна печатать пароль/рецепты/body в ответ или журнал. Следующий корректный запрос работает. Успешные поля/legacy-импорт/экспорт не меняются; malformed JSON не превращается в пустую книгу и не попадает в `PUT`-транзакцию.

Компоненты: `server.js` (`body`, media type guard, все семь мутаций), соответствующие API-тесты `tests/smoke.py` и описание контракта в документации. Нового schema validator/package не нужно. Не переводить любые исключения в 400: настоящие ошибки БД/IO остаются 5xx; менять только ошибки чтения/формы запроса.

Альтернативы: исправить только две разыменовки — меньше diff, но оставляет непоследовательность каталога/проб/logout; полностью строгая схема с библиотекой — большой новый объём. Рекомендуется общий ограниченный reader с проверкой контейнера и явным `allowEmpty` только для logout.

QA: матрица каждого маршрута × валидный object / `null` / `[]` / строка / число / boolean / malformed / empty / whitespace / чужой Content-Type / границы лимита. Setup проверять на новой временной базе, иначе 409 скрывает проверку тела. Login cases разнести по свежим серверам или между сериями выполнять корректный вход: иначе после 20 попыток ожидаемо срабатывает 429. Использовать реальные HTTP-ответы; при необходимости chunked body через встроенный `node:http`, без новой зависимости. Снять книгу/revision до и после, отдельно проверить сессию после rejected logout и отсутствие созданного пароля после rejected setup. Успешные save/promote/delete и конфликт revision работают по прежнему контракту.

## A10: воспроизводимые проверки и CI

**Факт:** `package.json` не содержит npm dependencies или lockfile. `npm run check` проверяет синтаксис пяти JS-файлов; `npm test` последовательно запускает Node test runner, Python Pillow test и Python Playwright smoke. В базе аудита прошло 2 + 1 + 43 = 46 проверок. В текущем этапе эти тесты повторно не запускались. `.github/workflows` отсутствует; зелёного CI пока нет.

Рекомендуется два результата без взаимной блокировки:

1. **A10 baseline, отдельный PR перед исправлениями:** закрепить среду, воспроизвести существующий набор, добавить CI check/test на PR в `main` и push в `main` без публикации. Исходный неуспешный regression-test для A04/A22 не включать в baseline как обязательный зелёный тест — он входит вместе с соответствующим исправлением.
2. **Регрессии в PR исправления:** A04/A22/A05 включают свою содержательную проверку, затем выполняют полный набор на commit PR. После A06/A07 добавить их согласованные сценарии. Это завершает покрытие A10, а не создаёт цикл «A04 ждёт A10, A10 ждёт исправленный A04».

Конкретный кандидат закрепления уже используемых инструментов: Node **24.19.0**, Python **3.12.14**, Pillow **12.3.0**, Python Playwright **1.62.0**. Версии Node/Python проверены командами, версии Python-пакетов — через `importlib.metadata` без установки. Это наблюдение текущей среды, **не** доказательство чистого CI. Вместо системного latest Chromium в CI использовать Chromium build, поставляемый зафиксированным Playwright 1.62.0; перед первым зелёным baseline записать реальный browser version/revision и зависимости ОС. Системный Chromium 154.0.8037.57 из старого аудита не выдавать за проверенную bundled-сборку Playwright.

Предлагаемые будущие файлы: `tests/requirements.txt` с точными версиями/хешами уже используемых Python-инструментов, `.github/workflows/tests.yml`, дополнение `docs/ARCHITECTURE.md` с командами и версионированием среды. Не добавлять production/npm-пакеты. Исполнимые команды установки и окончательный manifest должны пройти проверку в чистой среде; текущий документ не утверждает, что приведённые версии доступны на любом runner.

CI-проект: Linux runner семейства `ubuntu-24.04`, зафиксированные Node/Python patch versions, чистое Python venv и pinned browser. Checkout/setup actions закреплять reviewed commit SHA в реализации, а не выдумывать SHA в плане. Runner image и системные пакеты GitHub со временем меняются: для сопоставимости записывать image version, ОС, Node/Python/pip/Pillow/Playwright/browser version в артефакт прогона. Строго идентичный OS image потребовал бы отдельного согласованного container image digest; Docker не вводится молча ради этой задачи. CI должен повторять результаты на чистой поддерживаемой среде, а не обещать побайтовую идентичность runner.

Выполнить `npm run check`, затем `npm test`; установка npm для приложения не нужна. Для Playwright зафиксированный browser путь должен реально использоваться: `CHROMIUM_EXECUTABLE` указывать на bundled binary либо исключить fallback на случайный системный Chromium. Никаких `pull_request_target`, секретов production, выдачи write-permissions, deployment jobs и автоматического merge. Минимальные GitHub token permissions — `contents: read`. Временные `DATA_DIR`, без рабочей `.env`, синтетические fixtures; серверы и браузер завершать и очищать во всех исходах.

Артефакты сбоя содержат версии, имя теста, безопасный traceback и при необходимости скриншот синтетических примеров. Не выгружать SQLite/сессии/пароли/полные exports; не делать скрывающих flaky retry. Timeout/concurrency отменяют устаревший run, но не представляют его успешным. После намеренно внесённого нарушения в отдельной временной ветке CI должен быть красным; затем убрать эксперимент, без изменения `main`. Назначение required checks в branch protection — отдельное решение, A10 не меняет настройки репозитория самостоятельно.

Альтернативы: только runbook дёшев, но не защищает PR; pin существующего Python/Playwright и GitHub Actions даёт общий сигнал при ограниченном объёме; Docker digest повышает контроль ОС, но добавляет поддержку образа и не выбран в текущий минимум. Риск — несовместимая browser/OS пара и медленный CI; первый PR доказывает clean run до зависимости остальных PR от CI.

Приёмка: из чистой среды повторяются check и все существующие проверки; версии записаны; CI запускается на конкретном head commit PR и корректно падает при тестовом дефекте; не читает production data/secret и не публикует сайт. Два последовательных чистых успешных прогона baseline, без ретраев для скрытия нестабильности. Новые регрессии считаются только по фактическим результатам; число 46 — исходный ориентир, не зафиксированное навсегда требование.

Запросы по очереди могут прийти в обратном порядке; сохранить request token/abort и защиту stale results. Дедупликация save/trial неизменна |

A06 должен различать чтение/связь и результат записи: нельзя снимать «Не сохранено» только потому, что последующий polling GET успешен. Постоянный статус и действие должны опираться на реально завершённую мутацию; при ошибке редактора форма остаётся в памяти. Не обещать offline queue, persisted draft или повтор той же полной книги без проверки актуальной `revision`. Для короткого действия вне редактора повтор применяется к актуальному состоянию и проходит прежнюю очередь/409, а не отправляет устаревший снимок повторно.

### A07: минимальный additive API v1, ожидает одобрения

Текущее `GET /api/catalog` возвращает только `total`/`counts`; `/random` — один случайный рецепт. **API списка сейчас нет.** Не выдавать вывод списка за чистую CSS-правку и не отдавать JSON каталога как публичную статику.

Предлагается новый авторизованный `GET /api/catalog/list?q=&kind=&sort=title&offset=0&limit=12`. Старые `/api/catalog`, `/random`, `/art` и save routes сохраняются. У нового пути нет записи в SQLite и изменения revision.

- `q`: до 150 символов, прежняя семантика каталога — все значимые слова по title + ingredients, `ё`/`е`, существующее отсечение окончаний. Без fuzzy/morphology dependency, поиска в шагах или диетических обещаний.
- `kind`: пусто / `dish` / `mocktail` / `cocktail`; `sort`: `title` либо `time`, default `title`. Сортировка детерминированная: русское сравнение title для title; time по возрастанию для time, неизвестное время последним; tie-breaker `id`. Сейчас валидация каталога требует положительный time — новое состояние неизвестного времени этим не вводится. Настройки locale фиксируются и проверяются одинаковым корпусом в CI.
- `offset`: целое ≥0; `limit`: целое 1–48, default 12. Некорректные значения/пустые явно заданные числа →400, без молчаливого обрезания/NaN; offset за концом →200 и пустой `items`. Ограничить безопасными целыми числами. Порядок фильтрации/сортировки/пагинации документировать: сначала фильтр, затем sort, затем slice.
- Ответ: `{total, counts, matched, offset, limit, items}`. `total`/`counts` — весь каталог; `matched` — число совпадений q/kind до slice; `items` — ограниченная страница существующих полных recipe DTO с ID/источником/`art:`. Это позволяет открыть детали без ещё одного нового endpoint. Нет data URL семейных фото и чтения пользовательской книги в выдаче каталога.
- UI: 12 результатов и «Показать ещё», дополнительная порция не дублирует уже загруженные ID; при смене q/kind/sort offset=0. Поздний ответ старого запроса не заменяет новую выдачу. Возврат из деталей сохраняет q/kind/sort, загруженные страницы, позицию и фокус по ID в памяти открытого каталога. Новая сессия не обещает восстановление.
- «Случайная идея» остаётся отдельным действием прежнего `/random`. Сохранение использует прежний `catalogId`, `writeQueue` и идемпотентный save; повторный tap/две сессии не создают дубль, изменённая проба сохраняет своё содержимое при переносе.

Фильтры времени/инвентаря, персональные коллекции, persisted preferences и новая поисковая модель в этот API не включены. Улучшение поиска книги в A07 — ясные активные условия, счётчик/сброс/empty state и возврат к результатам без изменения семантики существующих `matchesQuery`/`filteredRecipes`.

Для независимого review разделить A07 на read API + контрактные тесты, затем UI выдачи/состояний. До второй части новый endpoint не виден в интерфейсе. Риск — ошибочная выдача/размер DTO; bounded limit и тесты стабильного порядка/границ достаточны для 1 567 неизменяемых записей. Серверная cursor-pagination, виртуализация и изменение полной книги — A11, отдельный объём.

## Небольшие PR, допуск и откат

Рекомендуемая последовательность после отдельного одобрения реализации: A10 baseline → A22 → A04 → A05 → согласованные A06 → A07 API → A07 UI. A22 и A04 технически независимы и могут иметь отдельные ветки; ручное объединение пересекающихся `tests/smoke.py` координируется PM. Регрессия каждого дефекта входит вместе с его исправлением. A05 и A06 не вести одновременно в одном CSS/HTML без согласования контрактов. Каждый diff проверяется QA на его head commit и передаётся владельцу отдельным PR; merge/deploy не выполняются агентами.

Откат каждого исправления/UI — отдельный revert соответствующего коммита после решения владельца, без замены/очистки SQLite и пользовательских JSON. A10 откатывается отменой workflow/manifest, не отключением проверок ради зелёного PR. A07 UI можно отменить, оставив совместимый неиспользуемый read endpoint; сам endpoint затем удаляется отдельным review при необходимости. Поскольку схема/формат данных не меняются, переноса данных для отката нет. Возврат к версии до исправлений A04/A22 возвращает известный дефект — этот риск указывается в решении, а не скрывается.
