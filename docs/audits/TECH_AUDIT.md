## Заключение

Текущая архитектура разумна для небольшой общей книги в домашней сети: один процесс, отсутствие npm-зависимостей, локальные ресурсы, SQLite/WAL, транзакции, защита от конфликтов и переносимость JSON. Она ещё не реализует утверждённую модель персонального облачного продукта. Наиболее важны изоляция пользователей, восстановление данных и безопасная эксплуатация, затем уменьшение объёма синхронизации и упрощение сопровождения интерфейса.

Рекомендуется **постепенное развитие в том же репозитории**: сначала исправления веб-качества на текущем стеке и выделение контрактов; затем TypeScript на границах и модульный Node.js backend; отдельно одобренный переход на PostgreSQL и личные аккаунты. React целесообразно проверить на одном сложном интерфейсном участке после согласования макетов. Полный rewrite и обязательный Next.js сейчас не обоснованы. Замена фреймворка сама по себе не исправит мобильную навигацию, контраст, полный PUT книги или отсутствие восстановления.

### Производительность: что измерено и что ещё нет

Измерены размеры файлов (`du`, `ls`, округлённые): `catalog/recipes.json` около 4,5 МиБ, image-index около 172 КиБ, 98 WebP-листов около 22 МиБ; `food-grid.png` 3 158 184 байта, кошка 2 266 450 байт, Halloween hero 2 031 891 байт; три TTF суммарно около 564 КиБ. Это **размер поставки на диске**, не объём загрузки каждой страницы: каталог JSON остаётся на сервере, а браузер берёт только нужные изображения. SVG-фрагменты иллюстраций используют целый WebP-лист (`app.js:115`), поэтому один рецепт может потребовать больше, чем его видимый фрагмент. Нельзя утверждать, что все 22 МиБ загружаются сразу.

Видимая авторизованная вкладка опрашивает сервер раз в 5 секунд с revision (`app.js:408`); неизменённая книга получает небольшой ответ. При 100 активных вкладках это примерно 20 запросов/с до учёта остальных действий — расчёт частоты, не проведённый load test. WebSocket не нужен до подтверждения, что polling не отвечает требованиям.

План замера: фиксировать версию браузера, CPU, сеть, состояние кэша, тему, объём книги и размер фото; отдельно cold/warm navigation, поиск, открытие редактора, save/favorite/import. Следить за долгими задачами, пиком памяти и transferred bytes. Для согласования — ориентиры Core Web Vitals из PRODUCT; локальный headless замер не равен полевому 75-му перцентилю.

### Безопасность и данные

URL источника ограничен HTTP(S), пользовательский текст экранируется (`app.js:112`, `app.js:127`, `server.js:64`); тесты содержат проверки вредоносных данных. По одному чтению нельзя выдавать полное отсутствие XSS/CSRF. Сейчас сервер проверяет Origin, если он передан, но допускает его отсутствие; сравнение host не проверяет все свойства origin (`server.js:117`). Перед облаком нужны негативные тесты scheme/port/Host, отсутствие Origin и определённая политика для будущих мобильных клиентов. SameSite и JSON Content-Type являются дополнительными мерами, а не универсальной моделью авторизации.

Фото проверяется по data URL и длине строки, не декодируется и не анализируется сервером (`server.js:70`). При будущей отдельной загрузке потребуется проверка фактического формата/размеров, квоты, безопасная обработка и приватная выдача. Все доступные сейчас изображения статики — встроенные иллюстрации, а пользовательские фото приходят в авторизованном JSON; нельзя переносить их в публичный bucket без контроля доступа.

CSP в ответах не настроен; вводить его стоит после инвентаризации inline SVG/style/script, сначала в report-only на согласованном окружении. Нет доказанного эксплойта только из-за отсутствия CSP. Содержание рецептов, base64-фото, пароли, cookie и экспорт нельзя писать в логи или отправлять внешней аналитике. TLS, шифрование носителя/копий и регион хранения — часть будущего эксплуатационного решения.

| Next.js route handlers + отдельные domain/repository модули | Меньше развёртываемых приложений при выборе Next; M–L | Связь с веб-runtime, connection pooling и приватный кэш; mobile API всё равно нужен | Разумно только вместе с обоснованным выбором Next; не держать бизнес-логику исключительно в UI/Server Actions |
| Supabase: managed PostgreSQL/Auth/Storage | Меньше собственной auth/backup-инфраструктуры; M–L | Регион/стоимость/лимиты/выход от провайдера; RLS и storage policies требуют отдельной проверки, service-role может обходить RLS | Альтернатива после сравнения бюджета и требований; наличие сервиса не гарантирует изоляцию или резервирование фото |

Для Fastify подтверждена [модель схем валидации/сериализации](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/), для Supabase — [механизм Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security). Выбор конкретного поставщика и тарифов не выполнен; платные ресурсы не создавались.

Предпочтительная целевая форма — модульный монолит: веб-клиент → версионируемый HTTP API → application/domain logic → PostgreSQL. Бизнес-логика не обращается к DOM и не зависит от React. Один репозиторий и один backend проще обслуживать на текущем масштабе; микросервисы и Kubernetes не решают подтверждённую задачу. Для БД сначала достаточно параметризованного SQL с миграциями; ORM (например, Prisma/Drizzle) добавляет типизацию/инструменты, но также генерацию, собственную модель миграций и ограничения SQL. Конкретный ORM без прототипа и оценки запросов не выбирается.

Облачный минимум для согласования: runtime Node подходящей поддерживаемой версии, HTTPS proxy, PostgreSQL в приватной сети, секреты вне Git, минимальные права DB-role, persistence/backup, readiness, health alerts, обновления, документированный rollback. Managed PostgreSQL уменьшает работу оператора, но не отменяет restore drill. Для одного VPS ниже инфраструктурная сложность закупки, выше собственная ответственность; точные расходы зависят от региона, SLA, хранения фото и команды и здесь не выдумываются.

## Предварительный план SQLite → PostgreSQL

**Ничего из следующих шагов не выполнялось.** Это проект runbook. Реализация инструментов, репетиция на согласованной копии и особенно работа с реальной книгой требуют одобрения конкретного объёма. PostgreSQL как цель уже принят D011; повторно выбирать целевую БД не требуется.

### 1. Решения и инвентаризация до инструментов

Ответственные: Developer + QA, принадлежность и эксплуатационные параметры утверждает владелец. Зафиксировать версию приложения/схемы, revision, число/ID и общий объём рецептов, разбивку main/trial/favorite/catalog/custom, отсутствие необязательных полей, все settings и migration markers, типы image, сессии и TTL. Источник в рабочем окружении не открывать сервером: startup выполняет изменения (`server.js:18`, `server.js:74`, `server.js:90`). Получать согласованный snapshot, а обследовать уже изолированную копию.

Согласовать: кому принадлежит общая книга; нужна ли копия нескольким людям; правила регистрации/recovery; перенос или отзыв текущего общего доступа; RPO/RTO, окно недоступности, регион/оператор, бюджет и сроки хранения копий. Не создавать вымышленных владельцев по имени Mac/автору commit. Возможный безопасный вариант — перенести книгу в одно явно подтверждённое личное пространство, а дальнейшее совместное использование оформить отдельно.

### 2. Полная копия и доказательство восстановления

Снять согласованный SQLite-consistent snapshot через Online Backup API/поддерживаемый backup tool; альтернативно — остановить всех writers, корректно закрыть БД и скопировать согласованный набор файлов с учётом WAL. Не копировать отдельно живой `.sqlite`, не удалять WAL/SHM и не считать JSON-экспорт полным backup. [SQLite Backup API](https://www.sqlite.org/backup.html) описывает snapshot; конкретный инструмент выбирается при реализации.

Отдельно сохранить exact app commit/package, весь необходимый набор `art:`/`sample:` assets, image-index, каталог/атрибуцию, конфигурацию и секреты в защищённом хранилище вне Git. Записать manifest контрольных сумм и размер. Настройка темы находится в localStorage (`theme.js:3`), legacy-рецепты могут оставаться в IndexedDB/localStorage (`app.js:67`): это не строки SQLite. Перенос сервера сам по себе их не перенесёт. Для смены origin предусмотреть добровольный экспорт legacy-данных и инструкцию для темы; не очищать старый браузер.

Восстановить snapshot в изолированном окружении, проверить SQLite integrity_check, счётчики, ID, фото и доступ на копии. Зафиксировать длительность и результат; только существование файла backup не проходит этот барьер. Копии шифруются, доступ ограничен, пароль/сессии не попадают в отчёт.

### 3. Предлагаемая схема и отображение

Минимальный переходный вариант, а не окончательная ER-модель:

| Источник | Предлагаемая цель | Инварианты |
| --- | --- | --- |
| Общая книга | users + libraries(owner_user_id), позже отдельные memberships | У каждой книги один подтверждённый владелец; доступ проверяет сервер |
| recipes.id/content | recipes(library_id, id TEXT, content JSONB, version, created_at), с FK и уникальностью (library_id,id) | Старые ID могут быть slug, не только UUID; сохранить все известные и неизвестные поля, порядок массивов, null и отсутствие полей |
| settings.revision | library revision / совместимый адаптер + per-recipe version | Не переносить общую revision как глобальную блокировку всех пользователей; старый протокол сохраняет семантику 409 |
| password / sessions | users/auth credentials и user-scoped sessions по отдельному mapping | Общую сессию нельзя превратить в доступ ко всем аккаунтам; предпочтителен согласованный отзыв с повторным входом |
| migration markers | metadata исходной книги + версия новой schema migration | Не запускать legacy-нормализацию повторно над уже перенесёнными данными без доказанной необходимости |
| data URL | На первом переносе сохранить содержимое без перекодирования; выделение media — отдельный этап | Совпадают декодированные байты и mime; пользовательское фото не заменяется иллюстрацией |
| art:/sample: | Сохранить ссылки, каталог, index и совместимые assets | Каждый идентификатор разрешается в тот же ресурс; не считать ссылку самостоятельным фото |

JSONB сохраняет значение, но не исходное форматирование и порядок ключей объекта. Для полного аудита хранить исходный JSON snapshot в защищённом архиве; сравнивать семантическую канонизацию, а не побайтово JSONB. Проверить поддерживаемые PostgreSQL значения, Unicode/нулевые символы, точность чисел и epoch-ms timestamps; неподдерживаемую запись остановить и показать в отчёте, не «исправлять» молча. Не превращать createdAt=8 из примера в текущее время и не назначать недостающие БЖУ нулями.

Начать с гибридной модели: ownership/версии/индексы — явные колонки, payload — JSONB для сохранения совместимости. Позже нормализовать ингредиенты/теги только при нужных запросах. Unique catalogId в области книги нужно согласовать с поведением импорта: импорт изменённой копии может дать другой ID с тем же catalogId; существующие данные нельзя отвергнуть новым ограничением без решения.

### 4. Изоляция и совместимость API

Каждый service/repository запрос ограничивает library_id и подтверждённого пользователя; клиентский owner_id не считается доказательством доступа. FK и составные ограничения должны запрещать связь чужого фото/рецепта/коллекции. При RLS использовать непривилегированную runtime-role, проверять работу через настоящий пул соединений; superuser/service-role не является проверкой RLS. Общий каталог остаётся read-only и отделён от пользовательских данных.

После появления нескольких аккаунтов старый PUT целой книги не должен ни видеть, ни удалять данные другой книги. Минимум — scope одной library и транзакционная блокировка/CAS revision. Новое API операций — отдельный совместимый этап с version/If-Match, идемпотентностью для повторного save/promote и договорённой семантикой DELETE. SQL BEGIN IMMEDIATE и SQLite INSERT OR REPLACE не переносятся механически: PostgreSQL требует своих транзакций, ON CONFLICT и конкурентных проверок.

Для мобильного будущего документировать DTO, ошибки 400/401/403/404/409/413/429, пагинацию, auth и версии API. Web-cookie остаётся хорошим вариантом для same-origin браузера; токены для native — отдельное решение с безопасным хранением/отзывом, не причина сейчас заменить всё на JWT.

### 5. Повторяемая тестовая миграция

После одобрения создать versioned tool, читающий только snapshot и пишущий в пустой staging PostgreSQL. Служебный migration_id связывает источник, контрольную сумму и версию mapping. Dry-run строит отчёт ошибок; перенос выполняется в транзакции/согласованных батчах, повтор не размножает данные; при ошибке публикации не происходит. Логи содержат ID/счётчики, без payload, хешей доступа и фото.

Репетиция использует синтетический набор с обеими полками, избранным, каталогом, копиями, источниками, legacy methods, steps/instructions, Unicode, нулевыми/неизвестными БЖУ, пропущенными полями, custom data URL и пустыми фото. Затем отдельно разрешённая обезличенная/защищённая копия при необходимости. Не подключать staging к production-базе и не использовать реальные учётные записи.

### 6. Сверка и приёмка до переключения

QA формирует протокол для **каждой** записи, а не выборки:

- Совпадают множества ID в каждой книге и число main/trial/favorite; отсутствуют лишние и пропущенные записи.
- Семантически совпадают все поля payload; порядок ingredients/steps сохранён, `steps.join('\n')` соответствует instructions там, где steps был; неизвестные поля и отсутствие optional не потеряны.
- Совпадают хеши декодированных фото; все art/sample ссылки разрешаются, app/assets manifest совпадает; источники и атрибуция сохранены.
- Settings имеют явный mapping: перенос, архив или согласованный отзыв; ни один ключ не потерян без записи решения. Hash старого пароля сохраняется только при совместимой согласованной auth-модели, без попытки расшифровать пароль.
- Работают вход/выход/recovery, CRUD, избранное, пробы, каталог, дедупликация, старый JSON import/export, перезапуск, две сессии и конфликты.
- Пользователь A не читает и не меняет B через списки, прямой ID, поиск, export, photo, promote/delete, stale revision; права сохраняются после рестарта.
- Выполнено восстановление PostgreSQL в новое изолированное окружение; права и ссылки на фото работают после restore.

Любое необъяснённое расхождение блокирует переключение. Сохранить безопасный отчёт счётчиков/хешей отдельно от пользовательских payload.

### 7. Резервирование PostgreSQL и фото

Согласовать управляемые ежедневные/иные snapshots, retention и проверку свежести исходя из RPO; при требовании меньшей потери — WAL archiving/PITR. Конкретная периодичность пока предложение владельцу. [PostgreSQL Backup and Restore](https://www.postgresql.org/docs/current/backup.html) различает SQL dump, файловые копии и continuous archiving. SQL dump не включает сами внешние media, конфигурацию окружения и все свойства инфраструктуры; состав полного backup нужно описать явно.

Если фото позже вынести в private object storage: сначала скопировать без перекодирования, хешировать, сохранить mapping и версии объектов, проверить authenticated retrieval и rollback. DB backup и media snapshot должны образовывать согласованную точку восстановления. Удаление «неиспользуемых» объектов — после retention и подтверждённой возможности отката. План с data URL в JSONB проще для первого переноса, но оставляет размер БД и сетевые накладные расходы; это временный trade-off, не идеальная конечная media-модель.

### 8. Управляемое переключение

Предпочтение для текущего масштаба — короткое согласованное окно без записи: заблокировать **все** writers (PUT, import, favorite, catalog save, trial actions), дождаться очередей/завершения запросов; снять финальный snapshot и revision; выполнить повторяемый перенос и полный отчёт; запустить совместимую версию на PostgreSQL; провести smoke в закрытом режиме; только после успешных критериев открыть запись. Старые вкладки должны получить понятный maintenance/upgrade ответ и перечитать состояние.

Если окно не укладывается в согласованный RTO, прежде проектировать delta journal/другую доказанную схему догоняющих изменений. Наивный dual-write в SQLite и PostgreSQL не даёт атомарности и не рекомендуется как «простой» способ нулевого простоя. Переключение не совмещать с полным редизайном и сменой frontend-фреймворка.

### 9. Откат, включая новые записи

Триггеры: нарушения целостности/изоляции, неработающий вход, ошибки критических CRUD, превышение согласованных порогов ошибок/задержек, невозможность восстановления. Ответственный и максимальное время решения известны до окна.

До открытия записи — вернуть прежний app commit/config и неизменённый SQLite snapshot, проверить revision и smoke. После открытия записи в PostgreSQL **нельзя просто вернуть старую SQLite**: новые рецепты, фото, правки и удаления потеряются. Остановить запись, сохранить PostgreSQL snapshot и журнал изменений после cutover; выполнить заранее отрепетированный обратный mapping только в новую копию SQLite с полной сверкой. Нужны tombstones/учёт удалений, photo bytes и сохранение ID, а не добавляющий JSON-импорт, который не воспроизводит удаления. Старые source files остаются неизменными.

Если новая модель уже содержит несколько персональных книг, старое приложение не умеет безопасно обслуживать их: откат должен быть к предыдущей совместимой PostgreSQL-версии либо к закрытому read-only режиму, а не слиянию всех книг в одну SQLite. До допуска новых моделей определить rollback boundary. При отсутствии проверенного обратного пути держать сервис в безопасном режиме восстановления и исправлять вперёд, сохраняя все изменения; не объявлять восстановление из старой копии «без потери данных».

После стабилизации сохранить исходный snapshot и assets на согласованный срок; удаление исходных данных и выключение старой установки — отдельное действие владельца. В этом аудите ни перенос, ни очистка не производились.

Product Manager получает варианты A/B как основу ближайших UI-работ; React/Next — отдельный доказательный пилот, backend/ORM — отдельное предложение. Владелец рассматривает конкретный объём из [IMPROVEMENT_PLAN](IMPROVEMENT_PLAN.md), регистрацию/принадлежность старой книги, RPO/RTO, бюджет/регион, права на каталог и при необходимости offline scope (Q2–Q4, Q6–Q9). Эти вопросы не препятствуют завершению аудита и не означают повторного выбора уже утверждённой персональной стратегии.
