# План улучшения «Крошки»

Дата: 22 октября 2026. Ведущая роль: Product Manager; основания — [продукт](PRODUCT_AUDIT.md), [UX/UI](UX_UI_AUDIT.md), [конкуренты](COMPETITOR_RESEARCH.md), [техника и PostgreSQL](TECH_AUDIT.md), [QA](QA_AUDIT.md). База `main` — `6aa62ee`, PR №1 и №2 объединены.

**Статус: предложение для рассмотрения владельцем.** Этот документ не разрешает изменение приложения, установку зависимостей, миграцию, деплой или слияние. В данном PR меняются только исследовательские документы и изображения тестового интерфейса. После review владелец выбирает конкретный объём, PM фиксирует версию и одобрение по [AGENT_WORKFLOW](../AGENT_WORKFLOW.md).

## Как читать приоритеты и оценки

- **P0** — условия допуска к публичному персональному сервису и работе с реальными данными. Это подтверждённые пробелы готовности, а не заявление об уже случившейся утечке или потере.
- **P1** — подтверждённые проблемы и важные улучшения основных веб-сценариев следующего этапа.
- **P2** — расширение удобства и возможностей после базового качества.
- **P3** — долгосрочные гипотезы, которые требуют отдельного подтверждения потребности.

Сложность относительная: **S** — локальное изменение, **M** — несколько связанных частей/состояний, **L** — изменение контрактов/хранения/безопасности, **XL** — несколько самостоятельных проектов. Это не количество гарантированных дней. Для каждого пункта ниже сформулированы проблема, решение, польза, сложность, риски, зависимости и приёмка. Целевые значения предложены для согласования, а не уже достигнуты.

## Рекомендуемый порядок на 4–8 недель

Это **сценарий планирования**, не обещание уложить весь backlog в восемь недель. Отсчёт после одобрения конкретного объёма; доступность команды, устройств и решения владельца могут сдвинуть этапы. Схема зависимостей: веб-дефекты можно исправлять параллельно проектированию безопасного облака; реальный перенос и публикация остаются отдельными решениями.

Нативные приложения, полный rewrite, OCR, pantry и AI в этот горизонт не входят. Нет необходимости одновременно менять frontend, auth, API и БД: это затрудняет проверку причин регрессий. Рекомендуется сначала локально улучшить web, затем вводить персональный backend по одному проверенному сценарию.

## Технологическая рекомендация и решения владельцу
