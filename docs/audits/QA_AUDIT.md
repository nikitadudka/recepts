## Воспроизведённые дефекты

Приоритеты: P0 — блокер сохранности или безопасного публичного запуска; P1 — существенно мешает основному сценарию; P2 — следующий этап. Классификация здесь — предложение QA для согласования с Product.

### QA-01 — P1: обновление при открытом диалоге оставляет каталог устаревшим

**Условия:** Chromium, 1440×1000, авторизованная страница со встроенными примерами; изменение выполнено вторым API-запросом с действующей тестовой сессией, что воспроизводит действие другого устройства.

**Шаги:**

1. Открыть «Чечевичный суп с овощами» в просмотре.
2. Получить актуальные `revision` и `recipes` через API; изменить только название этого рецепта на «QA обновление с другого устройства», отправить корректный `PUT /api/library`.
3. Дождаться polling страницы (подтверждено получение ответа с новым снимком, не `unchanged`).
4. Закрыть диалог через Escape. Проверить карточку сразу и после следующего пятисекундного polling.
5. Снова открыть этот рецепт.

**Фактически:** старый заголовок остаётся и в открытом просмотре, и на карточке после закрытия и следующего polling. При повторном открытии просмотр показывает новое название, хотя карточка ещё старая. Это подтверждает рассогласование state и DOM, а не неуспешную запись сервера.

**Ожидается:** при закрытии диалога отложенное обновление отражается в каталоге. Для открытого рецепта нужен согласованный способ уведомить об изменении, сохранив позицию чтения и незавершённые правки редактора.

**Последствия:** пользователь видит противоречивые версии; может принять старый список ингредиентов или шагов за актуальный во время совместной готовки. В этом сценарии потери данных на сервере не обнаружено.

**Причина по коду:** `app.js:37`–`40` принимает снимок и revision, но не вызывает `render()` при открытом диалоге; `app.js:319` и `327` закрывают просмотр без применения отложенной перерисовки. Следующий `unchanged` уже не вызывает `render()`.

**Решение и приёмка:** отслеживать отложенное обновление; после закрытия синхронизировать каталог, в просмотре показывать уведомление об изменении. Добавить регрессию с открытым просмотром и редактором, remote edit/delete/promote и закрытием через Escape, крестик и backdrop. Ни один сценарий не должен терять draft, а карточка после закрытия должна соответствовать принятой revision.

### QA-02 — P2: JSON `null` превращает ошибку входных данных в HTTP 500

**Условия:** тот же временный сервер; корректный `Content-Type: application/json`. Для PUT — авторизованная сессия.

**Шаги:** отправить literal `null` в `PUT /api/library`, затем в `POST /api/login`.

**Фактически:** оба запроса отвечают HTTP 500 с общей серверной ошибкой о чтении/сохранении книги. `/healthz` после них — 200; процесс не завершился. Ветка setup с `null` в этом опыте не проверялась, поскольку пароль уже задан.

**Ожидается:** контролируемая ошибка структуры запроса (400; для login возможен выбранный контрактом 400/401), без вводящего в заблуждение совета о диске.

**Последствия:** плохая диагностика интеграций и повреждённых импортов/API-клиентов; ложные серверные ошибки. Утечка или потеря данных этим опытом не доказана.

**Причина по коду:** после JSON parsing используются `input.password` (`server.js:136`–`137`) и `input.revision` (`server.js:207`–`208`) без проверки top-level non-null object; общий catch возвращает 500 (`server.js:233`).

**Решение и приёмка:** валидировать контейнер запроса до чтения полей; проверить `null`, массивы, строки, пустое тело, битый JSON, неправильный Content-Type и границы размера на всех изменяющих маршрутах. Ошибки клиента возвращают документированный 4xx, состояние книги/revision не меняется, следующий корректный запрос проходит.

## Главные пробелы и риск до следующего этапа

1. **Нет подтверждения полного восстановления.** JSON round-trip — полезная проверка, но не восстановление всей SQLite, настроек, WAL и ресурсов. Автоматические копии в приложении отсутствуют. До переноса данных это P0 release gate: доказать восстановление согласованной копии и определить допустимую потерю данных/время восстановления.
2. **Нет изоляции аккаунтов в реализации.** Нынешняя общая книга не должна проверяться как будто у неё уже есть пользователи. Для будущего облака обязательны негативные проверки чужих ID, списков, фото, экспорта и любых мутаций, а также восстановление доступа и отзыв сессий. До этих доказательств публичная персональная платформа не готова.
3. **Нет реальных мобильных браузеров.** Viewport не воспроизводит iOS keyboard/visual viewport, безопасные отступы, back/forward, memory pressure, фон/возврат, камеру, share/download и работу касанием.
4. **Нет достаточного аудита доступности в тестах.** В них есть отдельные клавиатурные действия и reduced motion, но нет полного обхода клавиатурой, screen reader, проверки имён диалогов/ошибок, контраста всех состояний, 200%/400% zoom. Результаты UX-проверок находятся в отдельном отчёте и не превращают набор smoke в сертификацию WCAG.
5. **Нет нагрузочного профиля и бюджета.** `PUT /api/library` передаёт весь снимок с data URL фото; сервер синхронно обрабатывает SQLite/crypto. Тестовый лимит 10 000 записей не означает удобство такой книги. Нужны данные 10/100/1000/10000, варианты с фото, несколько сессий и throttling.
6. **Воспроизводимость и CI недостаточны.** JS test runner встроенный, но Python/Chromium версии не закреплены репозиторием; CI-конфигурации в дереве нет. Возможны различия между машинами и пропуск регрессии до review.
7. **Недостаточно негативных сценариев.** QA-01/02 показывают пределы зелёного набора: не покрыты отложенная перерисовка и top-level JSON. Нужны также обрыв соединения в момент записи, истечение сессии во время редактирования, граничные фото/импорт и отсутствие места без реальных пользовательских данных.

## Рекомендация QA и передача

Документационный аудит можно передавать владельцу с указанными ограничениями. Текущая локальная версия имеет работающий регрессионный набор, но публичный запуск и перенос данных не готовы к приёмке: нужны доказанное восстановление, аккаунты с изоляцией, облачная защита и проверка реальных устройств. Отсутствие этих будущих возможностей не объявляется новым доказанным взломом локальной книги.

Следующие ответственные: Product Manager связывает QA-01/02 и пробелы с IMPROVEMENT_PLAN; UX/UI Designer & Researcher задаёт поведение обновлений/ошибок; Developer / Architect оценивает конкретные изменения. Реализация и новые регрессионные тесты начинаются после одобрения соответствующего предложения владельцем. Результаты этого аудита не являются разрешением на миграцию, деплой или слияние.
