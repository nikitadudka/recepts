# «Крошка»: инструкции для ИИ-агентов

Общий репозиторий: `nikitadudka/recepts`. Язык обсуждений и документации — русский. Продукт — семейная книга рецептов; текущая версия работает на домашнем Mac. Веб-сервис и мобильные приложения — направление развития, а не готовые возможности.

## Общая точка входа

Перед задачей прочитайте этот файл, [PRODUCT](docs/PRODUCT.md), [ARCHITECTURE](docs/ARCHITECTURE.md), [ROADMAP](docs/ROADMAP.md), [DECISIONS](docs/DECISIONS.md) и относящиеся к задаче части [README](README.md). Проверьте более узкие `AGENTS.md`, если они появятся. Команды и пути сверяйте с кодом и `package.json`.

- Код определяет фактическое поведение; документация объясняет его. При расхождении укажите источник и исправьте описание в рамках задачи. Не выдавайте план или гипотезу за реализацию.
- Все роли используют эти документы и один репозиторий. Личные чаты и память агента не заменяют общую документацию.
- Сначала изучите задачу, `git status`, текущую ветку, diff и затрагиваемый код. Не перезаписывайте чужие незакоммиченные изменения.
- Делайте минимальное законченное изменение. Не совмещайте задачу со случайным рефакторингом, переформатированием больших файлов или обновлением зависимостей.

## Роли и границы ответственности

| Роль | Ответственность | Результат и передача |
| --- | --- | --- |
| Product | Сценарии семьи, приоритеты, критерии приёмки, вопросы владельцу | Уточнённая задача; изменения PRODUCT/ROADMAP; предложение решения в DECISIONS |
| UX/UI Researcher | Исследование сценариев, мобильный интерфейс, доступность, сравнение решений | Выводы с источниками, макет или спецификация состояний; передача Developer и QA. Интервью проводятся только с разрешения владельца |
| Developer | Код клиента и сервера, совместимость данных, установка | Небольшой PR, обновлённая документация, проверки и инструкция для QA |
| QA | Независимая проверка критериев, регрессий, сохранности данных | Воспроизводимые дефекты, окружение и результаты проверок; рекомендация о готовности |

Это рабочие роли, не учётные записи в приложении. Один агент может совмещать роли, явно отмечая самопроверку. Доступность независимого QA не предполагается автоматически. Исследователь и Product не меняют код приложения без соответствующей задачи. Ни одна роль не утверждает за владельца изменение структуры, публикацию или слияние в основную ветку.

## Совместная работа

1. Для задачи зафиксируйте в GitHub Issue или описании PR: цель, ведущую роль, исходный commit, границы, затрагиваемые файлы, зависимости, критерии приёмки и требуемые решения владельца. Не создавайте дублирующие задачи, если запись уже есть.
2. Перед параллельной работой согласуйте файлы и контракты. Особенно координируйте `app.js`, `server.js`, `index.html`, стили и общие документы. Для разных задач используйте отдельные ветки и рабочие каталоги/worktree того же репозитория. Не переключайте ветку в каталоге работающего агента.
3. Изменение API или полей рецепта сначала опишите для Developer, Product и QA. Владелец утверждает изменение структуры приложения; агент не принимает его молча.
4. Передавайте результат письменно: ветка/commit/PR, что изменено, что проверено, ограничения, открытые вопросы, следующий ответственный. Документы также проходят review; у общей документации нет отдельных несовместимых версий по ролям.
5. При конфликте изменений остановите запись в пересекающиеся файлы, сравните намерения и согласуйте объединение. Не используйте принудительную перезапись для разрешения конфликта. Решения, влияющие на другие задачи, внесите в DECISIONS.

## Работа с кодом и данными

- Сейчас используются обычные HTML/CSS/JavaScript, Node.js ES modules и встроенный SQLite. Сохраняйте существующий подход. Новый фреймворк, пакет, база, разделение на сервисы или перенос файлов требуют отдельного предложения и согласования структуры.
- Сохраняйте совместимость старых рецептов и JSON-копий: необязательные поля, старые названия способов, `steps`/`instructions`, `shelf`, источники и изображения. Валидация сервера и клиента должна оставаться согласованной.
- Не ослабляйте проверку `revision`, транзакции, очередь сохранения, защиту от дублей каталога и устаревших действий со списком проб. `PUT /api/library` передаёт всю книгу и может удалить отсутствующие записи.
- Не удаляйте существующие файлы и данные. Удаление, необратимое преобразование или миграция реальной семейной базы требуют отдельного явного разрешения владельца, резервной копии и проверенного восстановления.
- Разработку и тесты ведите с отдельным временным `DATA_DIR`, никогда с рабочей книгой семьи. Не запускайте сервер на реальных данных ради проверки: при старте выполняются миграции.
- Не запускайте сценарии подготовки каталога просто для проверки: они перезаписывают JSON и/или иллюстрации. Меняйте набор рецептов и изображений только в соответствующей задаче; сохраняйте идентификаторы, атрибуцию и согласованность image-index с WebP.
- В UI учитывайте обе темы, телефон и компьютер, клавиатуру, подписи полей, фокус, ошибки сети, пустые состояния и `prefers-reduced-motion`. Пользовательский текст экранируйте; URL и изображения валидируйте.

## Проверки

Требуется Node.js >=22.13. Сборки и установки npm-пакетов для обычного запуска нет.

```sh
npm run check
npm test
```

`npm test` последовательно запускает `tests/install.test.js`, `tests/images_test.py`, `tests/smoke.py`. Нужны Python 3, Pillow, Python Playwright и Chromium; `CHROMIUM_EXECUTABLE` может задавать путь к браузеру. Тесты используют временные базы. Подготовку окружения описывает [ARCHITECTURE](docs/ARCHITECTURE.md).

- Для изменений поведения выполните `npm run check`, соответствующие существующие проверки и перед готовностью PR — `npm test`. Для исправленного дефекта добавляйте содержательную регрессионную проверку; не пишите тест, повторяющий реализацию.
- Для изменений только документации проверьте факты, ссылки и `git diff --check`; новый тест или полный браузерный прогон не обязателен.
- Для UI проверьте обе темы и мобильную ширину; для хранения — конфликт двух устройств, перезапуск, импорт/экспорт и старые данные; для установщика — синтаксис и сохранение данных.
- Linux-тесты не подтверждают работу `launchctl`, Gatekeeper, Bonjour, firewall или сна на Mac. Перед релизом установщика нужна отдельная проверка macOS; перед мобильным релизом — реальные iOS/Safari и Android/Chrome.
- В отчёте приводите реально выполненные команды и результат. Ошибки окружения и пропущенные проверки отмечайте отдельно; не объявляйте их успешными. Не ослабляйте тесты ради зелёного результата.

## Безопасность

- Не коммитьте `.env`, пароли, токены, cookie, SQLite/WAL/SHM, семейные JSON-экспорты и личные фотографии. В примерах используйте вымышленные данные. Не выводите секреты в логи, задачи и PR.
- Не меняйте общий семейный пароль и не сбрасывайте базу без явной задачи. Сохраняйте scrypt, хеширование сессий, HTTP-only/SameSite cookie, проверку Origin, ограничения запросов, входа и списка статических файлов.
- Текущий HTTP-режим предназначен для доверенной домашней сети. Не открывайте порт 3847 в интернет и не представляйте `PUBLIC_URL` как готовое HTTPS-развёртывание. Перед внешним доступом нужен согласованный план из ROADMAP.
- Публикация сервиса, изменение доступа, подключение платных услуг и передача семейных данных внешним сервисам требуют явного разрешения владельца. Не добавляйте AI-генерацию, аналитику или внешние API по собственной инициативе.
- Сохраняйте лицензии шрифтов и сведения об источниках каталога. При публичном распространении отдельно проверьте права на контент; наличие MIT в README сборщика не является проверкой прав на первичные рецепты.

## GitHub и завершение задачи

- Основная ветка — `main`. Работайте в отдельной ветке, например `docs/<task>`, `feat/<task>` или `fix/<task>`.
- Не отправляйте коммиты прямо в `main`, не сливайте PR и не включайте auto-merge без явного подтверждения владельца для этих изменений. Это правило действует и при технической возможности записи в `main`.
- Не применяйте force-push, `reset --hard`, `clean -fd` или удаление чужих веток/работы. Для обычного обновления ветки используйте безопасное объединение без переписывания чужой истории.
- Коммитьте только файлы своей задачи, проверив staged diff. В PR укажите проблему, итоговое поведение, критерии приёмки, проверки и существенные ограничения. Незавершённые решения обозначайте draft-статусом.
- Перед передачей обновите затронутые PRODUCT/ARCHITECTURE/ROADMAP/DECISIONS, проверьте `git diff --check` и отсутствие случайных файлов. В финальном отчёте дайте ссылку на результат и вопросы владельцу.
